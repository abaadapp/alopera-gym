# سير العمل: المهام والطلبات والدمج

## القاعدة الأساسية

- مهمة واحدة = Issue واحد = فرع واحد = Pull Request واحد.
- لا يُعدَّل `main` مباشرة أبدًا، والدفع المباشر إليه لا يُنشر (Main Gate يرفضه).
- **الدمج في `main` هو النشر على الإنتاج** (docs/DEPLOY.md)، فلا يدمج إلا صاحب النظام أو من يأذن له صراحةً.

## من البرومبت إلى الدمج

1. **البرومبت:**
   - تُكتب المهمة في GitHub Issue من قالب «Alopera Gym Development Task» (`.github/ISSUE_TEMPLATE/task.yml`).
   - حقول القالب: النوع، والحالة، والمسؤول، والأولوية، والملفات، والفرع، والاعتماديات، و**البرومبت**، والملاحظات.
   - أو يُرسَل البرومبت لـClaude في المحادثة، فينشئ هو الـIssue من القالب نفسه.
2. **التنفيذ:**
   - وسم `claude:ready` على الـIssue يشغّل Claude Code في GitHub Actions (`.github/workflows/claude-code-agent.yml`).
   - أو يشغّله Claude من جهازك بالقواعد نفسها (`AI_COMMAND_CENTER/EXECUTION_PROTOCOL.md`).
   - يعمل في فرع المهمة وحده، ويضيف الاختبارات ويشغّلها، ويفتح Pull Request إلى `main` فيه `Closes #N`.
   - الحالة تنتقل من `In Progress` إلى `In Review`، أو إلى `Blocked` إذا فشل.
3. **المراجعة:**
   - CI على الطلب: PHP وJS وTypeScript وPint والبناء، ثم إثبات الشجرة المختبَرة.
   - صاحب النظام يراجع التقرير والطلب، فإما `Changes Requested` وإما `Ready to Merge`.
4. **الدمج:**
   - بموافقة صاحب النظام الصريحة على هذا الطلب، من GitHub أو بأمر لـClaude في المحادثة: «ادمج #N».
   - يُدمج بـ Merge commit عادي، دون Force Push.
5. **بعد الدمج تلقائيًا:**
   - Main Gate، ثم Deploy Main، ثم فحص الموقع، ثم الوسم `v0.N`.
   - الحالة تصبح `Merged`، ثم `Done` بعد التحقق من النشر.

## دورة العمل لكل مهمة

1. حدّث `main` محليًا.
2. أنشئ فرعًا جديدًا من `main`.
3. سجّل المهمة في الـIssue، مع اسم المسؤول واسم الفرع.
4. نفّذ التعديل داخل الفرع فقط.
5. قبل فتح الطلب، اسحب آخر تغييرات `main` إلى الفرع. إذا تحرّك `main` أثناء الاختبار، يرفض إثبات CI الطلب حتى يُحدَّث.
6. شغّل الاختبارات المعنية، ثم الكاملة إذا كان التغيير في مسار حساس.
7. افتح Pull Request إلى `main`.
8. لا يتم الدمج مع وجود تعارضات، أو اختبارات فاشلة، أو نطاق غير واضح.
9. بعد الدمج، غيّر حالة المهمة إلى `Merged`، ثم إلى `Done` بعد التحقق.

## منع التعارض بين المسؤولين

- لكل مهمة مسؤول أساسي واحد وفرع واحد قبل البدء.
- إذا كانت مهمتان تلمسان الملفات نفسها أو المجال نفسه:
  - لا يبدأ الطرف الثاني تعديلًا كبيرًا قبل التنسيق.
  - الأفضل تقسيم العمل حسب الملفات، أو الطبقات، أو التسلسل.
  - إذا لزم العمل بالتوازي، فطلبات صغيرة ومتكررة بدل طلب ضخم.

## حالات المهام المعتمدة

`Backlog` · `Ready` · `In Progress` · `Blocked` · `In Review` · `Changes Requested` · `Ready to Merge` · `Merged` · `Done`

## الأولوية

| الأولوية | المعنى |
|---|---|
| `P0` | عطل حرج، أو سلامة بيانات، أو مشكلة في الإنتاج |
| `P1` | مشكلة مهمة جدًا، أو مانع إطلاق |
| `P2` | تحسين أو نقص مهم |
| `P3` | تحسين منخفض الأولوية |

## قاعدة Pull Requests

كل طلب يجب أن يحتوي على:

- وصف المشكلة أو الهدف.
- الملفات أو النطاق المتأثر.
- كيف تم اختبار التعديل.
- أي مخاطر أو آثار جانبية محتملة.
- رقم المهمة من GitHub Issue (`Closes #N`).

## Definition of Done

- مدموج في `main` بعد CI ناجح وموافقة صاحب النظام.
- نُشر، ونجح فحص الموقع، ووُسم (`v0.N`).
- الـIssue محدَّث: الفرع، ورابط الطلب، والاختبارات، والحالة `Done`.
